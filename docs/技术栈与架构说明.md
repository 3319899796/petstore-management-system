# 技术栈与系统构成说明

> 用途：帮你（和你答辩时的自己）用一句话讲清每一层在干什么、为什么这么选。
> 对应代码：`src/backend`（后端，已完成 L1）、`src/db/schema.sql`（数据库）。

---

## 一、一句话架构

**浏览器里的 Vue 页面 →（HTTP + JSON + JWT 令牌）→ Spring Boot 后端 → MyBatis-Plus → MySQL。
后端每个请求依次穿过「登录拦截器 → 权限切面 → Controller → Service → Mapper → SQL」。**

前后端彻底分离：后端只输出 JSON，不渲染页面；前端只管画界面，不碰 SQL。

---

## 二、技术栈：每一样东西是什么、干什么

| 技术 | 在本项目里的角色 | 为什么选它 |
| --- | --- | --- |
| **Spring Boot 2.7** | 后端的"骨架 + 总装车间"：内置 Tomcat、自动配置、依赖注入（IoC） | 开题报告已定；一个 `main` 方法就能跑起来，不用配 web.xml |
| **Spring MVC**（Boot 内置） | 把 HTTP 请求映射到 Java 方法（`@RestController`） | 与 Boot 一体，学习成本最低 |
| **MyBatis-Plus 3.5** | 持久层：单表增删改查不用写 SQL，复杂查询仍可手写 `@Select` | 比纯 MyBatis 少写 70% 样板代码，又不像 JPA 那样"看不见 SQL"；答辩能讲清每条 SQL 从哪来 |
| **MySQL 8.0** | 存 9 张表的数据 | 开题已定；教务机器普遍能装；InnoDB 支持事务和外键 |
| **JWT（jjwt 0.11.5）** | 登录凭证：登录成功发一张"签名门票"，之后每个请求带着它 | 无状态、前后端分离友好、不依赖服务器内存里的 session |
| **BCrypt** | 密码哈希 | 自带随机盐、刻意慢，数据库泄露也无法反推明文 |
| **Maven** | 依赖管理与打包 | 声明式依赖 + 一条命令打出可执行 jar |
| **Lombok** | 省 getter/setter | 实体类只写字段，代码更短（答辩时说明这是编译期注解，不影响运行） |
| **Vue 3 + Element Plus + Vite**（L6 才做） | 前端界面：表格、表单、弹窗、菜单 | 组件库现成，毕设界面能做得像样；Vite 启动快 |

**没有引入（且开题报告明确不引入）**：Redis、微服务、消息队列、Quartz、Spring Security 全量框架。
理由写在开题报告"系统边界"里：单机部署、用户量小、毕设周期有限，引入它们是负担而不是亮点。

> 注意：这里只用 `spring-security-crypto` 这一个 jar 拿 BCrypt，**没有**引入 Spring Security 的过滤器链，
> 所以登录鉴权是我们自己写的拦截器 + 切面，逻辑完全可控、每行都能讲。

## 三、系统构成：分层与目录

```
src/backend/
├── pom.xml                                 依赖清单（Maven 的"购物单"）
└── src/main/
    ├── resources/application.yml           端口、数据库连接、JWT 密钥与有效期
    └── java/com/ningcong/petstore/
        ├── PetStoreApplication.java        启动类（@SpringBootApplication + @MapperScan）
        ├── common/                         横向支撑：所有模块共用
        │   ├── Result.java                 统一响应体 {code, message, data}
        │   ├── ResultCode.java             状态码枚举 200/400/401/403/404/500
        │   ├── BusinessException.java      业务异常（"芯片号已存在"这类）
        │   └── GlobalExceptionHandler.java 全局异常 → 统一 JSON
        ├── config/                         装配
        │   ├── BeanConfig.java             BCryptPasswordEncoder
        │   ├── MybatisPlusConfig.java      分页插件
        │   └── WebConfig.java              注册拦截器 + 跨域
        ├── security/                       认证与授权
        │   ├── JwtUtil.java                签发/校验令牌
        │   ├── AuthInterceptor.java        第一级：验令牌（401）
        │   ├── RequirePerm.java            @RequirePerm 注解
        │   ├── PermAspect.java             第二级：验权限码（403）
        │   ├── LoginUser.java              当前用户 + 权限集合
        │   └── UserContext.java            ThreadLocal 传递当前用户
        ├── entity/                         与表一一对应的实体
        │   ├── SysUser.java                用户（表 sys_user）
        │   └── Role.java                   角色
        ├── mapper/                         数据访问（MyBatis 接口）
        │   ├── SysUserMapper.java
        │   └── RoleMapper.java
        ├── dto/                            入参对象（LoginDTO）
        ├── vo/                             出参对象（LoginVO）
        ├── service/                        业务逻辑（AuthService）
        ├── controller/                     接口层（AuthController、DemoController）
        └── init/DataInitializer.java       启动时建 3 个演示账号
```

**分层的意义**（答辩常被问"为什么要分层"）：
- Controller 只做"收参数、调 service、包 Result"，不写业务；
- Service 写业务规则和事务边界，抛 `BusinessException` 表达"不允许"；
- Mapper 只碰数据库；
- 改了数据库字段，只需动 entity + mapper，界面层不受影响——这就是"高内聚、低耦合"。

## 四、一次请求的完整链路（以"登录"为例）

```
1. 前端 POST /api/auth/login  {"username":"admin","password":"123456"}
2. Tomcat 收到 → 走到 AuthInterceptor
3. 该路径在 excludePathPatterns 里 → 放行，不要求令牌
4. AuthController.login() 收到 JSON → @Valid 校验非空
5. AuthService.login()
   ├─ SysUserMapper.selectByUsername("admin")  → SELECT * FROM sys_user WHERE username=? LIMIT 1
   ├─ passwordEncoder.matches(明文, 库里BCrypt)  → 比对（不解密，BCrypt 不可逆）
   ├─ RoleMapper.selectById(roleId)             → 取权限码串 "pet:list,pet:add,..."
   └─ JwtUtil.createToken(uid, username, rid)   → 生成签名令牌
6. 返回 Result{code:200,data:{token, roleName, permissions[...]}}
7. 前端把 token 存 localStorage，之后每个请求加请求头 Authorization: Bearer <token>
```

之后任一带令牌的请求：

```
AuthInterceptor.preHandle
 ├─ 取 Authorization → 去掉 "Bearer " → JwtUtil.parse（验签名+过期）
 ├─ claims.uid / claims.rid → RoleMapper.selectById(rid) 取权限
 ├─ UserContext.set(LoginUser)   ← 当前用户放进本线程
 └─ 放行
PermAspect（方法上有 @RequirePerm 才触发）
 ├─ 权限集合含 "*" → 放行
 ├─ 含任一所需权限码 → 放行
 └─ 否则抛 BusinessException(403) → GlobalExceptionHandler 转 JSON
业务方法执行 → 返回
AuthInterceptor.afterCompletion → UserContext.clear()（线程复用必须清）
```

## 五、两级鉴权怎么落地（开题报告"权限设计"那段的代码对应）

| 级别 | 位置 | 机制 | 效果 |
| --- | --- | --- | --- |
| 菜单级 / 按钮级 | 前端（L6） | 登录返回 `permissions`，前端按权限码渲染菜单与按钮 | 没权限的入口干脆不显示 |
| 接口级 | 后端 | `@RequirePerm("pet:add")` + `PermAspect` | 就算有人手搓请求绕过界面，也拿不到数据 |

三个角色的权限码（`role.permission` 字段，逗号分隔，`*` 为全部）：

- 宠物店管理员 `*`：全部功能
- 工作人员：宠物/主人/免疫/就诊的查询维护、寄养与领养审核、公告查看、数据看板
- 宠物主人：看自己的宠物、免疫与就诊记录、申请寄养、申请领养、看公告

- `pet.chip_no` 唯一索引：一只宠物一个芯片号，防重复建档

## 七、几个必须能讲清的设计决策

1. **为什么用户表叫 `sys_user` 不叫 `user`**：`user` 是 MySQL 保留字，建表和写 SQL 都要反引号，容易出错；改名后 SQL 干净。
2. **为什么用 JWT 不用 session**：前后端分离 + 多端（浏览器、以后可能的移动端）；JWT 不占服务器内存，水平扩展方便。代价是"注销"不能立刻让旧令牌失效——本系统用户量小、令牌 2 小时过期，可接受（这一句就是答辩的"权衡"）。
3. **为什么权限不放进 JWT**：放进去要等令牌过期才生效；现在每次请求按 roleId 查角色，改权限立刻生效，代价是每请求多一次主键查询。
4. **为什么回访不建新表**：回访是一对一、字段少（时间 + 结果），建表会让 9 张表变 10 张并多一次 join；用扩展字段更符合本系统规模。
5. **为什么提醒用 Spring Task 不用 Quartz**：单机、任务简单、每天跑一次即可；Quartz 需要额外表和管理界面，属于过度设计（开题报告"系统边界"已声明）。
6. **照片只存路径不存二进制**：数据库不膨胀、备份轻；文件放服务器目录，`pet.photo_path` 存相对路径。

## 八、环境与启动顺序（当前机器实测状态）

| 依赖 | 本机状态 | 需要做什么 |
| --- | --- | --- |
| JDK 17 | ✅ `C:\Program Files\Java\jdk-17`（17.0.12） | 无需安装 |
| Maven | ❌ 未安装 | 装 Maven 3.9.x，或直接用 IntelliJ IDEA 内置的 Maven |
| MySQL 8 | ❌ 未安装（3306 未监听） | 装 MySQL 8.0（记住 root 密码） |
| Node 18+ | ⚠️ 系统未装（DSH 自带 v24，仅供我这边用） | L6 做前端前装一个即可 |

启动顺序：

1. 装 MySQL → 用 root 执行 `src/db/schema.sql`（建库 `pet_store` + 9 张表 + 3 个角色）
2. 改 `src/backend/src/main/resources/application.yml` 里的数据库密码（或设环境变量 `MYSQL_PASSWORD`）
3. 用 IDEA 打开 `D:\论文毕设\src\backend`（识别 pom.xml），等依赖下载完
4. 运行 `PetStoreApplication`，控制台出现 `演示账号已创建：admin / staff / owner` 即成功
5. 自测三条（见 `docs/开发任务分解.md` 的 L1 验收）
