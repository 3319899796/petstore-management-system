## 五、7 条「失败」用例的复核结论

初跑时 84 条中有 7 条判定失败，逐条对照源码与数据库后确认**全部是测试脚本自身预期写错**，系统行为正确：

| 序号 | 表面现象 | 真实原因 | 处理 |
| --- | --- | --- | --- |
| 1 | 芯片号重复未被拒绝 | 脚本两次用了**不同**芯片号，自然都能建档 | 修正用例：复用同一芯片号，确认返回 400 |
| 2 | 7 天内到期数对不上 | 演示数据日期固定，测试当日为 11-25，days_left 为 -15/-5/1/3/6 | 修正预期为 5 |
| 3 | 领养申请被拒 | 该宠物已有待处理申请（业务规则：一宠物同时只能有一个） | 改用无申请的宠物 |
| 4 | 统计宠物数比预期多 1 | 前一条用例真实创建了 1 只未删除 | 修正预期，测试后清理 |
| 5 | 主人新增宠物被允许 | 设计如此（TC-26），主人可新增并自动归属自己 | 修正预期 |
| 6 | 到期疫苗数重复计数 | `vaccineDue7` 已包含逾期，脚本又叠加 `vaccineOverdue` | 修正为只取 `vaccineDue7` |
| 7 | 非法 JSON 返回 HTTP 200 | 统一返回体，错误码放在 body 的 `code` | 记录为设计取舍 |

结论：**本次实测未发现功能性缺陷**，7 条差异全部来自用例编写假设与系统实际设计的偏差，已全部修正用例并复跑通过。

## 六、已知设计取舍（答辩时可主动说明）

1. **统一返回体**：所有业务结果以 `{code, message, data}` 返回，业务错误多为 HTTP 200 + `code=500/400`；仅在鉴权（401）与越权（403）时设置 HTTP 状态码。优点是前端只需判断一处；缺点是不符合严格 REST 语义。
2. **JWT 无状态认证**：token 存前端 localStorage，服务端不维护会话，退出登录仅前端清除本地 token，无法服务端强制下线。
3. **权限表达式**：`@PreAuthorize` + 权限串（如 `notice:publish`），角色与权限在数据库配置，可扩展。
4. **数据隔离在 Service 层实现**：主人角色查询时强制拼接 `owner_id = 当前用户`，而非依赖前端传参。
5. **疫苗到期为每日定时任务 + 查询时兜底计算**，二者结果一致。

## 七、复现步骤

```bat
REM 1. 启动 MySQL（数据目录 D:\petstore-rt\mysql-data，配置文件 D:\petstore-rt\tools\my.ini）
REM 2. 建库建表
mysql --host=127.0.0.1 --port=3306 --user=root --password=123456 < src\db\schema.sql
REM 3. 启动后端（首次启动自动创建 admin/staff/owner 三个账号）
java -Dfile.encoding=UTF-8 -jar src\backend\target\pet-store-1.0.0.jar
REM 4. 导入演示数据（后端首次启动之后执行）
mysql --host=127.0.0.1 --port=3306 --user=root --password=123456 --database=pet_store < src\db\demo-data.sql
REM 5. 执行接口测试
node _tmp\api_test.mjs
node _tmp\api_test2.mjs
```

注意：`demo-data.sql` 必须在后端首次启动**之后**导入，因为三个登录账号由后端初始化器创建。
