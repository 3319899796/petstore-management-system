# 答辩现场演示脚本（8 分钟走完，按顺序点）

> 前置：MySQL 已执行 `schema.sql` + `demo-data.sql`，后端 `mvn spring-boot:run` 已在跑，前端 `npm run dev` 已打开 `http://127.0.0.1:5173`。
> 建议提前把三个浏览器标签分别登录 admin / staff / owner，答辩时直接切标签，省去反复登录。

## 0. 开场一句话（10 秒）

「这是一个宠物店的信息管理系统，服务三类人：宠物店管理员、工作人员、宠物主人。技术上用 Spring Boot + MyBatis-Plus + MySQL 做后端，Vue 3 + Element Plus 做前端，前后端分离。」

## 1. 管理员登录 → 看板（1 分钟，展示"数据看得到"）

用 **admin / 123456** 登录，停在看板页：

- 指着 6 个卡片说：这是宠物总数、主人总数、待审核寄养、寄养中、待审核领养、领养完成率
- 指着柱状图说：近 6 个月新增宠物数，SQL 是 `GROUP BY DATE_FORMAT(create_time,'%Y-%m')`
- 指着饼图说：免疫到期分布，逾期 / 7 天内 / 30 天内 / 更久
- 拉到下面"7 天内到期免疫提醒"表格：豆豆的狂犬疫苗 `daysLeft = -13` 标红，"这些是系统算出来的，不是我手填的"

## 2. 宠物档案 + 照片（1 分半，展示"增删改查"）

进「宠物管理」：

1. 搜「豆」→ 只剩豆豆（演示模糊查询）
2. 选主人「李娜」→ 只剩可乐、布丁（演示关联筛选）
3. 新增一只：名称「雪球」、芯片号 `CHIP-CAT-0007`、品种布偶猫、主人王强，**上传一张照片**
   - 说完一句："照片存本地磁盘，数据库里只存路径，符合开题报告里'不上对象存储'的边界"
4. 再新增一次同样芯片号 → 提示「芯片号「CHIP-CAT-0007」已存在」（演示唯一性校验）
5. 删豆豆 → 提示「该数据已被其它记录引用，无法删除」（演示外键保护，说明"数据不能乱删"）
6. 删刚建的雪球 → 成功

## 3. 权限对比（1 分钟，这是本系统的"骨架"，一定要演示）

切到 **owner / 123456** 标签：

- 左侧菜单只有 6 项，**没有看板、没有主人管理、没有用户管理**
- 宠物管理里只有豆豆、汤圆（看不到别人的宠物）
- 免疫记录里没有"新增/编辑"按钮

切到 **staff / 123456** 标签：

- 有看板、免疫、就诊、寄养审核、领养审核
- 没有「用户管理」「公告管理」

然后补一句关键说明（老师最爱问这个）：

> 「菜单隐藏只是前端体验。真正的权限在后端：每个接口上有 `@RequirePerm("xxx")`，切面比对当前角色的权限码，不匹配直接返回 403。比如工作人员手工发一个新增用户的请求，照样被拒——测试用例 TC-09 就是专门验这个的。」

## 4. 免疫提醒（1 分半，本项目最有"业务含量"的部分）

回到 **admin** 标签，进「免疫管理」：

1. 打开「只看即将到期」开关 → 只剩 2 条（3 天后、5 天后到期）
2. 展示一条记录的 `daysLeft` 计算：「到期日减今天，前端标红标黄」
3. 新增一条：接种日期选今天、周期留空 → 保存后"下次到期日"自动变成一年后（演示 `DEFAULT_CYCLE_DAYS = 365`）
4. 进「公告管理」，点 **「立即执行提醒扫描」** → 提示「已生成 N 条提醒」
5. **再点一次** → 提示「已生成 0 条提醒」

> 这时候说："这就是 `vaccine.reminded` 标记位起的作用——生成过就置 1，所以定时任务每天跑不会重复刷屏，这是幂等设计。定时任务本身是 `@Scheduled(cron = "0 0 9 * * ?")`，每天 9 点自动扫，答辩现场我用接口手动触发了一次，效果一样。"

6. 打开一条提醒详情，念内容：「【疫苗到期提醒】豆豆的狂犬疫苗，主人张伟，上次接种 2025-11-10，到期 2026-11-10，已逾期 13 天」

## 5. 寄养 / 领养状态机（2 分钟，展示"流程留痕"）

**寄养**（owner 提交 → staff 审核）：

1. 切 owner：给豆豆提交 2026-12-01 至 2026-12-05 的寄养 → 生成「待审核」
2. 再提交一个 12-03 至 12-08 → 提示「该宠物在该时间段已有寄养安排」（演示重叠校验）
3. 切 staff：审核通过 → 状态变「寄养中」，处理人记录为当前操作人
4. 点「结束寄养」→「已结束」
5. 试着删除已结束记录 → 提示不能删（演示状态机保护）

**领养**（owner 申请 → admin 审核 → 过户 → 回访）：

1. 切 owner：申请领养李娜名下的「布丁」
2. 再申请自己的豆豆 → 提示不能申请自己的宠物
3. 切 admin：审核通过。**这时打开宠物管理看布丁的主人**——已变成申请人
   > 「通过的一瞬间做了两件事：改 adoption 状态、把 pet.owner_id 改成申请人，这两步在同一个事务里，所以不会出现'申请通过了但宠物没过户'的脏数据。」
4. 切 staff：对该记录填回访结果「已适应新家，进食正常」→ 保存
   > 「回访没单独建表，用的是 adoption 表的 `follow_up_time` / `follow_up_result` 两个扩展字段——因为开题报告定了 9 张表，这是设计取舍，不是漏做。」

## 6. 越权验证（30 秒，加分项）

用 staff 的 token 在 PowerShell 里发一个管理员接口：

```powershell
curl.exe -X POST http://127.0.0.1:8080/api/user `
  -H "Content-Type: application/json" `
  -H "Authorization: Bearer <staff的token>" `
  -d '{\"username\":\"hacker\",\"password\":\"123456\",\"roleId\":1}'
```

返回：

```json
{"code":403,"message":"缺少权限：user:edit","data":null}
```

> 「菜单看不到只是第一层，接口层才是真正的门。」

## 7. 收尾（30 秒）

> 「系统按开题报告的功能点全部落地：登录与权限双控、宠物档案一户多宠、主人信息脱敏、免疫与就诊、寄养领养状态机留痕、到期提醒、统计分析。数据库 9 张表，代码分层 Controller-Service-Mapper，前端 10 个页面。本机测试用例 85 条，关键路径全部通过。」

## 万一出问题的备用方案（提前准备）

| 出问题的环节 | 备用说法/做法 |
|---|---|
| 前端起不来 | 直接演示后端接口（curl / Postman），并打开 `docs/接口清单.md` 讲契约 |
| 数据库连不上 | 提前录一段 2 分钟的屏幕录像兜底 |
| 照片上传报错 | 说"演示环境没配上传目录"，跳过，讲代码 `FileStorageService` 的校验逻辑 |
| 定时任务没触发 | 说明现场用手动触发接口替代，cron 表达式念出来即可（每天 9 点） |
| 老师问"这是你写的吗" | 打开 `docs/零基础读代码指南.md` 与 `tools/check_backend.py`，说明每层职责与自检方式；强调正文本人独立完成，AI 只用于查错与文档整理 |
